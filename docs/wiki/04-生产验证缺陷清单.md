## D1 ·【高】四个自助端点在线上全部 404，修复从未发布

**现象**：同一 id、同一合法凭证，只差路径形态：

| 请求 | 结果 |
| --- | --- |
| `PATCH /api/submissions/<id>/withdraw` | `404 {"message":"未找到提交记录"}` |
| `PATCH /.netlify/functions/submissions-withdraw/<id>` | `200 {"id":"…","status":"withdrawn"}` |
| `PATCH /api/submissions/<id>/visibility` | `404 未找到提交记录` |
| `PATCH /.netlify/functions/submissions-visibility/<id>` | `400 该状态的记录不支持隐藏`（**说明记录查到了**） |
| `PATCH /api/admin/submissions/<id>`（路径无动作后缀） | `200` 正常 |

**根因**：Netlify 的 status 200 proxy redirect 不改写 handler 看到的 `event.path`，末段是动作名。线上把 `withdraw`/`visibility`/`delete`/`revisions` 当成投稿 id 去查库。这正是提交 `608a4b5 fix(submissions): 修正自助端点把动作段当投稿 id 导致线上全部 404` 修的问题——**修复在仓库里、有单测（`tests/submissionSelfService.test.ts` 的「线上路径形状」一组），但从未部署**。

**证据链**：生产前端徽章 `v0.9.0`，而仓库 HEAD 的 `src/data/changelog.ts` 首位是 `0.9.1`；`0.9.0` 对应的提交是 `2127813`（上线自助管理功能），`608a4b5` 在其后 26 分钟。`/me` 页面同时印着原始阶段 id 与角色 slug，则是 `9302c7e`（v0.9.1 排版修订）也没上线的表现。三个独立症状同源。

**用户影响**：`/me` 的**撤回、隐藏展示、删除记录、编辑并重新提交四个动作在生产全部不可用**，界面统一提示「未找到提交记录」。投稿者只能靠「忘记该凭证」清掉本机记录，无法自助管理任何一条已提交的记录。已通过记录的作者尤其没有任何出路。

**修法**：`pnpm deploy:netlify` 重新发布即可（代码已就绪）。发布后回归：
`curl -X PATCH <site>/api/submissions/<id>/withdraw -H 'content-type: application/json' -d '{"token":"…"}'` 应返回 `200 {id,status:"withdrawn"}` 而不是 `404`。

**判据补充**：`admin-submissions.ts` 无库分支会多带 `hidden`/`ownerToken` 两键——现在生产返回的键里**没有**这两个，可作为「SQL 分支生效」的旁证；但这条旁证只在库里无数据时容易看错，别单独依赖。

`src/components/admin/AdminSubmissionCard.vue:21-24` 的名称映射取自 `seedConfig`，而 `src/data/seed/config.json` 的 `bosses` 是**空数组** ⇒ 审核台卡片上「`<作者> · <模式> · <阶段>`」的第三段必然是原始 id：实测显示 `西木黑 · 异相仲裁 · 4.5-aa-checkmate`。模式名正确是因为 `seedConfig.modes` 有值。

**修法**：卡片改用 `useArchiveStore().loadConfig()` 的合并配置查 `bosses`/`units`，或最低成本先把阶段段换成 `stageLabelOf(bossId)`（`4.5-aa-checkmate` → 「将杀」）。**注意**卡片是纯展示组件，引 store 要连带处理挂载测试里的 `createPinia()`（`tests/MySubmissionsView.test.ts` 已有可抄的写法）。

> - 组件 **第 7 行已经** `import { categoryLabels, flagLabels, flagOrder } from "@/services/runUtils"` —— 要用的 `stageLabelOf` 就在同一个模块，**在同一行加一个名字即可**，不必新增 import，也不必碰 `seedConfig`（第 6 行仍被模式名使用，别顺手删）。

## D3 ·【中】withdrawn 记录在审核台错显「已驳回」且给全套按钮

`AdminSubmissionCard.vue` 的 `statusLabel()` 只有三档，`withdrawn` 落进 `else` ⇒ 实测在「全部记录」tab 里一条 `withdrawn` 记录的 chip 显示「已驳回」，并且三个按钮「通过并发布 / 驳回 / 退回待审」全部出现。

管理员因此**看不到「作者已撤回」这个真实状态**，还可能在一条作者主动撤下的记录上点「通过并发布」把它重新发布。叠加 `GET /api/admin/submissions?status=withdrawn` → `400 不支持的审核状态`（`withdrawn` 不在 `allowedStatuses` 白名单），撤回态在审核台侧几乎是隐形的。

**修法**：`statusLabel()`/状态色补第四档「已撤回」；`allowedStatuses` 加 `withdrawn`；`admin-submissions-id.ts` 要不要允许管理员直接改判 `withdrawn` 另议（目前只有作者侧能产生该状态）。

## D4 ·【低】通过动作会把旧的驳回原因带回记录

`src/composables/useAdminSubmissions.ts:41` 用 `review.reviewerNote` 预填每张卡片的备注框，`:90` 再把它随任意动作发出；服务端 `admin-submissions-id.ts:152` 的 `approved`/`rejected` 共用分支 `set status=…, reviewer_note=${body.note?.trim() || null}`。

实测：一条被驳回并写了原因的记录，管理员直接点「重新通过」（不动备注框）后，`reviewerNote` **仍是那条驳回原因**（复核取回：「接口验证：先驳回以验白名单」）。对读者没直接影响（该字段不外显），但审核台里挂着的是一条已通过记录配一句驳回理由，误导后续接手的人。

**修法**：`approved` 分支不沿用备注（前端在 `status==='approved'` 时发 `note:''`，或服务端 `approved` 时固定写 `null`）；若要保留「管理备注」语义，则按钮文案与占位提示要区分开。

## D5 ·【低】服务端缺纵深防御，脏数据可一路进公开档案

`netlify/functions/_shared.ts` 的 `validateSubmission()` 只检查 8 项**存在性**，21 条表单规则（枚举、值域、长度、域名、4+4 单位数）**全部只存在于 `src/services/submissionValidation.ts`**，函数侧一条都没有。

实测一份 `mode:"bogus"`、`cost:999`、`score:999999`、`category:"asScore4000"`（属于另一模式的分档）、只有 1 个角色 + 3 把光锥、`flags:["revive","不存在的标记"]`、外加未知字段 `__unknownField` 的 payload：`POST /api/submissions` **202 入队** → 管理员通过 **200** → 以 `mode=bogus`、`cost=999` 出现在公开 `runs` 里。

挡在最后的只有两道外键（`runs.season_id → seasons`、`runs.boss_id → stages`）和 `unitCost` 的钳位。而且：

- `runs.mode`/`runs.category` 是无 CHECK 约束的 `text`（`netlify/schema.sql`），任何字符串都进得去；
- `tags` 直接取 `payload.flags`，服务端不过滤非法标记（读取侧靠 `flagsOfRun()` 收窄，写脏了不影响展示，但库里是脏的）；
- `runs.cost` **不随队伍重算**，直接抄 `payload.cost`，所以 999 能进公开表；
- 唯一真正的隐患在 `admin-submissions-id.ts`：**只有请求体解析那一处包了 `try/catch`（`:20-24`），写库分支没有**（原登记写作「整段没有 try/catch」，措辞过粗，易被误读为连 body 解析都没保护）。因此脏 payload 撞上外键（例如 `bossId` 不在 `stages` 里）时直接 `500`，并且**先 upsert 出一条 `name=bossId` 的最小占位 `stages` 行**——那行没有任何端点能删。
  - **成因比"缺 try/catch"更具体**：`:58/:89/:95/:124/:137` 是**逐条 `await sql` 顺序执行、整段无事务包裹**（全文件 `begin`/`transaction` 零命中），而占位 stages 行在 `:89-92` 就落库、`insert into runs` 在 `:95` 才执行。⇒ 光加 try/catch 把 500 变成 502 **并不能回收那一行**；修法 2 的「`bossId` 不在快照里就拒绝通过」只挡住了这一种情形，任何**后续**写入失败同样会留下已提交的 stages 行。彻底解法是把这一串写包进同一事务（或先完成全部校验再开始写）。

**修法（按性价比）**：
1. 把 `submissionValidation.ts` 的枚举/值域判定抽成函数侧可复用的纯模块（`videoUrl.ts`/`runFlags.ts` 已是这个模式：无 `@/` 值导入、函数侧相对引用），入队时至少校 `mode ∈ EndgameMode`、`category ∈ categoryOptionsFor(mode,bossId)`、`0 ≤ cost ≤ 48`、`units.length===lightcones.length===4`、`isUsableVideoUrl`。
2. `admin-submissions-id.ts` 的 approved 分支包 try/catch，失败返回 `502` 中文提示而不是 `500`；`bossId` 不在快照里时**拒绝通过**而不是造占位行；并把 `stages` upsert → `runs` insert → `run_units` 重建这串写**包进同一事务**，否则 try/catch 只改状态码、回收不了已提交的占位行（见上一条成因）。
3. `GET /api/archive/runs` 的 `?bossId=` 缺省是 `""`（seed `bosses` 为空 ⇒ `parseFilters` 兜不到值），带任何合法筛选都要显式传 `season`+`mode`+`bossId`，否则恒 0 条——容易把「查询写错」误读成「库里没数据」。

`sub_1788932641243_l4e4bp`、`sub_1788932946944_u7ducc`、`sub_1788933560417_ivakau`。

## D13 ·【高·发布链路】`pnpm deploy:netlify` 在本机装不上 netlify-cli，且失败会被管道掩盖成成功

2026-09-12 实际执行发布时踩到，**这是当前唯一阻塞 D1 上线的东西**：

```
[ERR_PNPM_NO_MATCHING_VERSION] No matching version found for
@netlify/serverless-functions-api@^2.21.2 while fetching it from https://registry.npmmirror.com/
This error happened while installing the dependencies of netlify-cli@27.5.2
```

- **根因**：`deploy:netlify` 走 `pnpm --package=netlify-cli dlx netlify deploy`，每次都要现装 CLI；而本机 pnpm 与 npm 的全局 registry 都是 `https://registry.npmmirror.com`（`pnpm config get registry` 可证），镜像上该依赖最新只到 `2.19.1`（2026-08-14 发布），装不出来。仓库自己的 `.npmrc` 只设了 `auto-install-peers` / `strict-peer-dependencies`，**镜像来自用户级配置**。
- **最危险的一点**：`pnpm deploy:netlify … | tail -40` 的退出码是 `tail` 的。我第一次就这样把**已失败**的发布读成了 exit 0 —— 构建门禁全绿、`dist` 已产出新哈希，但线上包哈希纹丝不动。判发布是否生效**只能看线上资产哈希与 `0.9.1` 字样**，不能信管道退出码。
- **两条无效绕过**（都实测过）：`npm_config_registry=https://registry.npmjs.org` 前缀对 dlx 无效；`pnpm dlx --registry=…` 直接报 `Unknown option: 'registry'`。
- **可用绕过**：不动任何全局配置，装到隔离前缀再直接调它的 bin ——
  `npm install --no-save --prefix /tmp/nfcli --registry=https://registry.npmjs.org netlify-cli@27.5.2`
  然后 `XDG_CONFIG_HOME="$PWD/.netlify-config" /tmp/nfcli/node_modules/.bin/netlify deploy --prod --dir=dist --functions=netlify/functions --no-build --site hsr-endgame-archive-cn --message "…"`（登录态在 `.netlify-config/configstore` 里，与 dlx 无关）。

**建议的根治**：给 `scripts/deploy-netlify.sh` 加一层「CLI 已存在就复用」的判据，并在脚本末尾显式 `echo "deploy exit=$?"` 而不是让调用方的管道吞掉退出码；或把 netlify-cli 提为 devDependency 锁版本，避免每次现装。

> ⚠️ **成因仍未定论**：绕过法**确实完成了发布**（deploy `6aa580aea06f6a359d2eedf6`，线上包 `index-OiGqnFis.js` → `index-vWHDuzRE.js`、含 `0.9.1`），但「这就是 `608a4b5`（2026-09-09 17:13）三周没上线的原因」这条**没能证实**——netlify-cli v27 的 `api` 子命令取不到 deploy 历史：`--params` 不是合法选项、`--data '{"site_id":"<站名>"}'` 报 `Missing required path variable`、`getSite` 用站名返回空。要定论得先拿到 numeric site id（控制台 Projects → Settings → Global settings 里可见），再 `netlify api listSiteDeploys --data '{"site_id":"<numeric>"}'`。在此之前，这条只作为**高概率假设**，别写进结论。

### 一处踩坑（记下来避免再犯）

neon serverless **1.1.0** 的 `sql.unsafe(stmt)` 只产出 SQL 片段、**不会自己执行**：`await sql.unsafe("alter table …")` 返回的是 `{sql: "…"}` 而不是结果，四条 DDL 全部「成功」却没落库（`pg_constraint` 查不到）。要执行得写成 `await sql\`${sql.unsafe(stmt)}\``。同版本 `sql.transaction()` 是**非交互式**的——只接受查询数组或返回数组的非 async 函数，不能在回调里 `await`，所以审核写入那串是先构造数组再一次性提交。**判 DDL 是否真的生效只能查系统目录**，不能看调用有没有抛错。
