## 高：会导致线上行为错误或让校验静默失效

### H1. 服务端不校验标记值，与前端深链行为分歧

- **证据**：`netlify/functions/_shared.ts:165` `error TS2322: Type 'string[]' is not assignable to type 'RunFlag[]'`
- **问题**：`parseFilters()` 把 `?flags=` 直接 `split(",").filter(Boolean)` 塞进 `ArchiveFilters.flags`，**不判断是否为合法标记**。前端 `useArchiveFilters.normalizeFlags()` 却是丢弃非法值。于是同一个深链两种结果：

  | 输入 | 前端 | 服务端 |
  | --- | --- | --- |
  | `?flags=revive,bogus` | 只看「复活」，有结果 | 要求同时命中 `revive` 与 `bogus`，**空集** |

  筛选是 AND 语义，所以非法值不会「无影响」，而是直接把结果清空。站内检索链接会被用户互相转发，这条是会踩到的。
- **修复**：`netlify/functions/_shared.ts:169` 改 `.filter(isRunFlag)`；判定原语从 `runUtils.ts` 抽到 `src/services/runFlags.ts`（`runUtils` 带 `@/services/unitCost` 的值导入，Functions 打包不解析 Vite 别名而引不了），`runUtils.ts:21` 原样再导出以保持「唯一来源」不变。

### H2. `sql<T>` 泛型被忽略，SQL 返回类型从未被检查

- **证据**：
  - `netlify/functions/_shared.ts:360`、`:377` `error TS2558: Expected 0 type arguments, but got 1`
  - `netlify/functions/submissions-me.ts:43`、`:66` 同上
  - `netlify/functions/submissions-withdraw.ts:51` 同上
  - 连带 `netlify/functions/_shared.ts:395`、`:396` `error TS2345: Argument of type 'Record<string, any>' is not assignable to parameter of type 'DuplicateRow'`
- **问题**：neon 的 `sql` 标签模板**不是泛型函数**，`sql<DuplicateRow[]>\`…\`` 里的类型参数被完全丢弃，返回值实际是 `any`。也就是说这几处 SQL 的列名、别名、`as "xxx"` 映射从来没被类型验证过 —— `:395/:396` 就是它漏出来的证据：`toDuplicateMatch()` 拿到的是 `Record<string, any>`，与它声明的 `DuplicateRow` 毫无约束关系。
- **影响面**：投稿查重（`findDuplicateVideoRecords`）与「我的投稿」反查/撤回都走这些 SQL。改列名或 SQL 写错别名，以前不会有任何提示。
- **修复**：改成结果处显式断言 `(await sql\`…\`) as T[]`，让类型至少与真实列名对齐。

### H3. 配队预设把「未填」压成 0，载入后显示 E0/S0

- **证据**：`src/composables/useSubmissionMemory.ts:128`、`:129` `error TS2322`（`number | undefined` → `number`）
- **问题**：`SubmissionPresetSlot.eidolon` / `SubmissionPresetLightcone.superimposition` 声明为必填 `number`，而表单里这两个字段可以是「未填」。存预设时被强行要求是数字，语义上等于把「没选」变成「选了 0」。载入预设后命座显示 E0、叠影显示 S0，而用户原本可能是留空想走默认值逻辑。
- **修复**：`src/composables/useSubmissionMemory.ts:10`、`:15` 改为可选字段，载入后交回表单的默认值口径（`defaultEidolonFor` / `defaultSuperimpositionFor`）。

## 中：类型形同虚设，但不改变运行时行为

### M1. `SubmissionPayload` 的只读性与缺字段

- **证据**：`src/views/AdminSubmissionsView.vue:139` `TS2322`（`readonly RunFlag[]` 不能赋给 `RunFlag[]`）；`src/views/MySubmissionsView.vue:30` `TS2741: Property 'flags' is missing`；`tests/fixtures/config.ts:35` `TS2322`（`RunFlag[] | undefined`）
- **问题**：审核台从只读 store 取 payload 再传给组件，类型上要求可变数组；`MySubmissionsView` 构造的占位 payload 少了 `flags` 字段。
- **修复**：`src/types/archive.ts:218-220` 把 `flags` / `units` / `lightcones` 改为 `readonly`（全仓无 push/sort 用法，已核）；`src/services/unitCost.ts:79-80` 入参同步改 `readonly RunUnit[]`；`src/services/submissionUtils.ts` 落到可变的 `ArchiveRun` 时复制一份。

### M2. `vite.config.ts` 的 `test` 块从未被检查

- **证据**：`vite.config.ts:17` `error TS2769: No overload matches this call … 'test' does not exist in type 'UserConfigExport'`
- **问题**：vitest 2.1 的 `config.d.ts` 不做 `declare module "vite"` 增强，所以 `/// <reference types="vitest/config" />` 这条路无效；而改用 `vitest/config` 自带的 `defineConfig` 又会把它内部捆绑的 vite5 类型和项目里的 vite6 插件类型撞车（`Plugin<Api>` 不兼容）。
- **修复**：`vite.config.ts:8` 显式标注 `UserConfig & Pick<VitestUserConfig, "test">` 后再交给 `defineConfig` —— 仍是类型检查，不是 `as` 断言。

## 值得记住的三条

1. **「没有报错」不等于「检查过了」。** 这次最贵的发现不是那 43 个错误，而是 `pnpm typecheck` 从来没检查任何东西 —— 而且它以退出码 0 的样子表现得很好。凡是「门禁通过」的结论，值得偶尔往里看一眼它到底跑了什么。
2. **泛型标签模板是静默失效的典型。** `sql<T>\`…\`` 读起来像是在断言，实际类型参数被丢掉、返回值退回 `any`。这类写法（以及 `as` 到 `Record<string, any>`）不会在 review 里引起注意。
3. **前后端各一份的解析逻辑会漂移。** H1 的根因不是某个 bug，而是「前端丢弃非法值、服务端原样保留」这个分歧长期没人对齐。`runFlags.ts` 的存在就是把它变成一份实现。
