### 阶段 B：pending 态与凭证体系（curl，29 + 6 项）

`403 凭证不匹配`（错 token）、`404 未找到提交记录`（不存在 id）、`405`（GET 打 PATCH 端点）、`400 请求体不是合法 JSON`、`400 缺少或非法的凭证`（token >200 字符）、`400 hidden 必须是布尔值`（`"true"` 字符串）、`400 缺少投稿内容 missing:["payload"]`（含把 payload 字段拍平到顶层的误用）。

白名单三连：pending **不可**隐藏（`该状态的记录不支持隐藏`）、**不可**修订（`该记录不支持编辑重新提交`）、**不可**硬删（`只有已驳回的记录可以删除`）——正是 `/me` 上「pending 只给撤回按钮」的服务端对偶。

`/me` 的 token 处理：非数组短路 `{reviews:[],runs:[],hiddenCount:0}`；重复去重；两端空白 trim 后命中；`''`/`'  '`/`null`/`42` 被过滤而不影响真凭证；**上限 50 按插入序截断**（真凭证放第 51 位即查不到，放前 50 内正常）。

### 阶段 C：查重（curl，8 项）

`409` 的 message 与 `duplicate.matches[0].id` 精确命中；matches 形状 9 键；`source` 在「既是投稿又是公开记录」时**保留投稿侧**（`submission`）；换阶段放行；空链接/非法链接放行不报错；`excludeIds` 自我排除生效、**超过 8 条时第 9 项起静默丢弃**（不报错，实测仍能命中）；记录被硬删后查重放行。

- **`runs.owner_token` 确实写入** ⇒ `/api/submissions/me` 的 `runs` 数组能查到这条已通过记录（作者侧日后可自删的前提）。

另确认：编辑态 `unlockedIndex` 从 0 开始（`draft=null`）——三步要重走，是设计不是缺陷。

### 阶段 F：撤回 / 隐藏 / 硬删 / 就地重提（curl + 浏览器，38 项）

- 撤回：`200 {id,status:"withdrawn}"`，**重复撤回仍 200**（幂等短路）；错凭证 403。
- 隐藏：`withdrawn`/`rejected` 都放行、`pending`/`approved` 一律 400；重复设同值幂等；`/me` 默认视图按**家族**收纳并回 `hiddenCount:1`（修订随父一起），`includeHidden:true` 才全给；取消隐藏可逆。
- `/me` 的 `runs` 查询**不带 status 过滤** ⇒ 驳回后 `/me` 仍返回那行 `runs`（status=rejected 的「幽灵条目」）。这正是硬删必须 `runs` + `submission_reviews` 两张表一起清的原因，行为与文档一致。
- 就地重提（rejected 父）：**200 `{id:父, updated:true}`**、`status` 回 pending、`reviewer_note` 与 `reviewed_at` 双双清成 `null`、`hidden` 强制复位 `false`、**id 不变、队列行数不变**。
- 硬删：只认 `rejected`；`200 {deleted:true, removedRun:true}`；**不幂等**（二次 `404`）；删完 `run_units` 靠级联消失、查重放行。
- UI 动作矩阵与破坏性确认：pending=仅撤回；approved=编辑+撤回（无删除/隐藏）；rejected=编辑+隐藏展示+删除记录（无撤回）；「删除记录」第一次点击只展开「确认删除 / 取消」且**零请求**，点取消后仍零请求。

### 阶段 G：脏 payload 能走多远（curl，29/29）

`validateSubmission` 只做 8 项存在性校验，实测一份枚举、值域、长度、单位数全非法的 payload：**202 入队 → 审核通过 200 → 以 `mode=bogus`、`cost=999` 落进公开 `runs`**（`runs.mode`/`category` 是无约束 text，只有 `season_id`/`boss_id` 有外键）。

顺带量到三条口径：`limitedCount=7` 证明命座 99 被钳到 6（否则会是 100）；`cost=999` **不随队伍重算**（`runs.cost` 直接取 payload）；1 角色 + 3 光锥只算出 7 点成本，因为 `getUnitGoldCounts` **按下标把角色与光锥配对**，超出角色数的光锥不参与计成本。
好消息是脏记录仍能用「改判 rejected → 作者硬删」完全撤销，实测清干净了。风险面见缺陷页 D5。

## 复跑方法

1. 浏览器通道：`/api` 只能同源调用（函数完全没有设 CORS，也没有 OPTIONS 预检分支），所以跨域的 curl 脚本没问题、浏览器内只有站内 fetch 能用。
2. 本轮用的驱动脚本原在 `/tmp/hsrcdp/`（`cdp.mjs` 是无依赖的 CDP 客户端：Node 24 自带 `WebSocket`；`api.mjs` 封装带管理员头的调用）。**`/tmp` 重启即失，已复制一份到 `~/hsr-verify-harness-20260912/`**（60 个文件、3.9MB，含阶段截图；仓库本身仍零改动）。
   - **凭据安全性已扫描确认**：`api.mjs:3,11` 只从 `process.env.AU` / `process.env.AP` 取值，在调用时才拼 `Basic` 头；对全部脚本扫描 `Basic <字面量>`、`Bearer <字面量>`、`own_<hex>` **零命中**，只有投稿 id（本就写在本文档里，非机密）。⇒ 若要长期保留，把它们挪进 `scripts/` 在凭据上是安全的。
   - ⚠️ 挪进去时**只带 `.mjs`**：那 3.9MB 里绝大部分是 PNG 截图，不该进版本库。
   - 原文「建议补 `.mjs.d.ts` 声明」这句**多余**：`tsconfig.app.json` 的 `include` 是 `env.d.ts`、`src/**/*`、`tests/**/*`、`netlify/functions/**/*.ts`、`vite.config.ts`，**不含 `scripts/`**；现有 `scripts/*.mjs`（`reference-inventory.mjs`、`seed-archive-tables.mjs`、`sync-articles.mjs` 等）都没有 `.d.ts`，`pnpm typecheck` 照样通过。
3. 零残留判据始终是这两条：`GET /api/admin/submissions?status=all` 的 id 集合 == 开工前，且 `runs?season=4.5&mode=aa&bossId=4.5-aa-checkmate` 为 `[]`。
